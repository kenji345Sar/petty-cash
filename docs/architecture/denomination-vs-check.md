# 金種表と有高チェックの設計方針

## 金種（Denomination）と有高（DenominationCheck）の違い

### Denomination（値オブジェクト）

「万札○枚、千円札○枚...」という金種の枚数を表す。
金額計算のルールは1つだけで、どの文脈でも同じ構造・同じ計算式を使う。

```
1万円 × 3枚 = 30,000円
千円  × 5枚 =  5,000円
合計         = 35,000円
```

### DenominationCheck（エンティティ）

「実際に数えた結果」を記録する行為。
Denomination を使って実数を算出し、帳簿との差額を計算する。
差額がある場合は調整取引（Adjustment）を自動生成する。

### 使用箇所の対比

| 用途 | 意味 | 使用箇所 |
|---|---|---|
| 有高チェック | 実際に数えた枚数 | `DenominationCheck.Denomination` |
| 入出金の金種 | 取引に含まれる枚数 | `VendorTransaction.Denomination` / `PettyCashTransaction.Denomination` |

## なぜドメインを分けないのか

値オブジェクト `Denomination` は共通のまま、**意味の違いはエンティティが担う**。

- データ構造（万札○枚、千円○枚...）は同一
- 計算ルール（TotalAmount）も同一
- 違いは「何の文脈で使われるか」だけ

文脈の違いは以下が担当する：

- `DenominationCheck` に入っていれば → 有高チェックの記録
- `Transaction` に入っていれば → 取引の金種内訳

**ドメインを分けてしまうと：**

- 同じ計算ロジックを2箇所で保守することになる
- 片方だけ修正してもう片方に反映し忘れる事故が起きる
- 不要な複雑さが増える

## UI側での制御

金種フォームは共通のUIコンポーネント（`DenominationForm`）とし、
呼び出し元がコールバック（`onComplete` / `onCancel`）で戻り先と保存処理を制御する。

### コンポーネント設計

```tsx
// 共通の金種入力フォーム
<DenominationForm
  onComplete={(denomination) => {
    // 出納帳から → 金額入力欄にセット
    // 有高から   → APIで保存 + 調整取引
  }}
  onCancel={() => {
    // 呼び出し元の画面に戻る
  }}
  expectedAmount={...}  // 有高チェック時のみ。帳簿金額を渡す
/>
```

- `expectedAmount` がある場合 → 有高チェックモード（差額表示あり、保存ボタン）
- `expectedAmount` がない場合 → 金種入力モード（合計表示のみ、確定ボタン）

ドメインの責務ではなく、UIフローの違いはアプリケーション層・UI層で制御する。

## 有高チェック時の調整取引

有高チェックで差額がある場合、帳簿を実数に合わせるため調整取引を自動生成する。

### フロー

```
有高チェック実行
  ↓
DenominationCheck を記録（差額を計算）
  ↓
差額 ≠ 0 の場合
  ↓
Adjustment 取引を自動生成（符号付き金額）
  ↓
バッグの TotalAmount を実数に更新（バッグチェックの場合）
```

### TransactionType

| 値 | 意味 | 残高への影響 |
|---|---|---|
| Deposit (0) | 入金 | +amount |
| Withdrawal (1) | 出金 | -amount |
| Adjustment (2) | 有高調整 | +amount（符号付き。マイナスなら減算） |

### 残高SQL

```sql
SUM(CASE
  WHEN type = 2 THEN amount      -- 調整: 符号付きでそのまま加算
  WHEN type = 0 THEN amount      -- 入金: 加算
  ELSE -amount                   -- 出金: 減算
END)
```

## テスト方針

| テスト層 | 何をテストするか | 外部依存 |
|---|---|---|
| ドメイン | エンティティ・値オブジェクトのルール | なし |
| ユースケース | ユースケースの流れ（リポジトリはモック） | Moq |
| 統合 | DB含めた実際の動作 | PostgreSQL |

リファクタリング時は、先にテストで現在の動作を固めてから変更する（TDD）。
